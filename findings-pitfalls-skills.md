# Findings, pitfalls, skills — заметки для агентов

Рабочие заметки по «Крибил»: что ломалось, как чинилось, какие приёмы
оказались удачными. План-спецификация — в `plan-kribil-plainjs.md`,
сравнение веток — в `attempts-comparison.md`.

## Рантайм

- Каждый js-файл — IIFE-обёртка с `global.Kribil` и гардом
  `if (typeof module !== "undefined" && module.exports) module.exports = K;`
  (паттерн смотри в любом `js/*.js`). В браузере теги классические,
  порядок в `index.html` = порядок require-цепочек. Никаких import/export,
  никакого билда.
- `node --check js/*.js` ловит синтаксис; полноценно код под DOM в ноде
  проверяется jsdom: канвас 2d — через `new Proxy({}, {get:()=>noop})`
  (для create*Gradient вернуть `{addDivideStop(){}}`), добавить стабы
  `Path2D`, `ResizeObserver`, `HTMLDialogElement.showModal/close`,
  `canvas.setPointerCapture`, `getBoundingClientRect`, ручной
  `requestAnimationFrame` с очередью колбэков. readyState у jsdom остаётся
  `loading` — диспатчить `DOMContentLoaded` после загрузки скриптов.
- `node --test` без путей подхватывает ВСЕ файлы по маске тестов,
  включая `*.test.ts` в референсных каталогах `B-bots-failed/`,
  `GLM53f/`. Прогон ограничен glob'ом в `package.json`:
  `node --test tests/*.test.js`.

## Физика и симуляция

- Событие удара о борт называется **`cushion`**, не `rail` (один раз уже
  был баг в фильтре журнала UI). Контакт — `contact`, выстрел — `shot`,
  точка — `checkpoint`, финал — `finish`, полный покой — `rest`.
- 60 Гц видимых кадров недостаточно для физики: шары проходят мимо
  друг друга. В `runSim` каждый кадр дробится `sub` подшагами (3–4),
  детект точек и контактов — на подшаге, запись кадров — на fps.
- Точки семплируются (`nearest`) на fps, а не на подшагах: ближайшая
  дистанция может оказаться чуть больше радиуса (один кадр подлёта при
  скорости 3 м/с — это ≈0.025 м). Тесты и направляющий член это учитывают.
- Симуляция останавливается через 0.25 с полного покоя ПОСЛЕ применения
  всех ударов; после финиша держим `holdAfterFinish=0.4 с`, иначе
  окно прохождения последней точки не успевает замкнуться.
- Жёсткий лимит кадров `(maxTime + hold + 0.6)·fps` обязателен: на льду
  и при слабом трении шары катятся долго, без лимита траектория
  разрастается и подвешивает вкладку.
- Порядок тел стабилен: объект = 0, биток игрока p = p+1. `castRay`
  исключает `selfIdx = player+1`.
- Трение в модели линейное (вычитаем из модуля скорости), `stopEps`
  обнуляет скорость — без точной остановки «все шары встали» не
  срабатывает и runSim уезжает в лимит.

## Оптимизатор — главные грабли

- **Мульти-сид ансамбль (`attempts ≥ 3`) не убирать.** Для locked-
  расстановки конструкция отдельной ноги для конкретного сида может не
  иметь допустимой геометрии (биток уже за целью, нормаль контакта
  смотрит назад, одно-бортный банк возвращает null). Ни увеличение
  итераций (проверено до 120), ни 360°-перебор, ни спасение ног не
  чинят конкретный невезучий сид; у одиночного сида ~50% успеха на
  дуге. Три сида — ~100%.
- t и силу locked-ноги нельзя крутить как независимые координаты:
  момент удара τ = tArrive − tTravel связан с силой через время
  добегания. Нужен синхронный τ-sweep (`lockTimed`), иначе градиент
  дёргает два конфликтующих параметра.
- В free-режиме не возвращаться к travel-синхронной расстановке:
  рабочая схема — поставить биток рядом с ghost ball по касательной и
  планировать выстрел на `tArrive + 0.08`.
- При отклонении jitter-кандидата в free откатывать angle/power/t,
  а не только численную стоимость.
- Прямой удар нельзя принимать только по тому, что луч пересекает
  шар: проверять «попутность» нормали контакта (`fwd > 0.45` в
  конструкторе, `> 0.4` в rescueLegs), иначе выбирается биток, который
  толкает шар в обратную сторону.
- Любой кандидат должен использовать ОДИН результат `evaluate(cfg,state)`
  как `{cost,res}`: двойной вызов cost() в полировке давал устаревший
  res и кашу из стрелок.
- Жадный выбор ближайшего битка и сидирование из номинальной геометрии
  предыдущих неудач — тупик; вместо этого скоринг маршрутов (`routeOf`):
  прямой `1000 + fwd·200 − d·10`, банк `500 − len·30`.
- `rescueLegs` перестраивает только из того, до чего дозвонился общий
  план; если ранняя нога не проходится вообще — нужен каскад с k=0
  (реализован), но геометрию, которой нет для данной расстановки, он
  не создаст; страховка — ансамбль.
- `Solver.run(бюджет_мс)` гоняет генератор чанками и отдаёт прогресс;
  UI крутит его на rAF по 16–20 мс. Решение брать из
  `solver.out.best`/`solver.current`, НЕ из значения последнего yield.
- `cfg.seedPlan` (ручной план пользователя) подаётся только в попытку 0;
  остальные сиды стартуют со своих конструкторов.
- Сила под банкованные удары — с запасом ×1.25 (удлинённый путь + трение).

## Рендер

- Не аллоцировать `Path2D` и массивы корзин в каждом кадре. В `app.js`
  trail-кэш строится один раз на identity результата (`frames` +
  `count`), в живом режиме — не чаще чем раз в 6 новых записанных
  кадров; покадрово только `stroke()`.
- DPR: размер канваса умножается на devicePixelRatio, затем
  `ctx.setTransform(dpr,0,0,dpr,0,0)`, а view считается в CSS-пикселях.
  Ресайз — через `ResizeObserver` с дебаунсом, с обязательным сбросом
  trail-кэша.
- Стрелка удара рисуется от позиции битка В МОМЕНТ t (кадры траектории,
  `frames.at(t, player+1)`), а не от стартовой позиции: к поздним
  ударам биток мог укатиться.
- Голова стрелки: длина `0.1 + 0.62·min(1,power/maxPower)`; при
  перетаскивании инвертировать эту формулу для силы.

## UI-приёмы

- Прецизионный слайдер из ТЗ (10% хода ≈ +0.01, 100% ≈ +2):
  `Δ = sign(f)·scale·0.0168·(exp(4.8·|f|)−1)`, рычаг возвращается в 0
  на pointerup, double-click по числу — prompt для точного значения.
  scale: t=2.5, угол=90 (градусы), сила=1.
- Clipboard API запрещён в части file://-контекстов: копирование —
  фолбэк через `select()+execCommand('copy')` в модалке; вставка —
  поле для ручной вставки + попытка `readText()`.
- Не подменять ручной план пользователя при неудаче решателя: решение
  применяется к документу только при solved; предыдущие удары/позиции
  сохраняются в одноуровневый undo («вернуть мои удары»).
- После успешного применения решения ОБНУЛЯТЬ ссылку на solver —
  иначе activeRes() продолжает рисовать его устаревшие кадры поверх
  ручных правок.
- Пока решатель считает, редактирование холста запрещаем, но показываем
  его черновики (кадры, стрелки из `current.state`, метки таймлайна).
- Кнопки и пробел: если после клика кнопка осталась в фокусе, пробел
  и «кликает» кнопку, и срабатывает в глобальном хоткее — в keydown
  выходить для `BUTTON/INPUT/TEXTAREA`.

## Живой режим

- Физика в рантайме 240 Гц, запись 60 Гц; аккумулятор времени
  ограничен 0.06 с на кадр (защита от скачков после фоновой вкладки).
- У человека кулдаун 0.28 с, у ботов — `PLAYERS[p].cool`; без кулдауна
  зажатие мыши/тик бота превращается в пулемёт.
- Бот должен вернуть null, если удара нет в принципе (дальность,
  следующая точка уже далеко) — тогда движок коротко переставляет его
  кулдаун, а не долбит каждые 60 мс.
- Полностью ботовая партия (человек бездействует) должна финишировать
  сама — это smoke-критерий; на дефолтном зигзаге ~25–30 с. С человеком
  быстрее не гарантировано (он может мешать), это нормально.

## Найденное в референсных ветках

- GLM `vec.ts`: `clamp` без `return` — ошибка молча ломала все
  ограничения, которые на неё опирались. Урок: каждое математическое
  ограничение должно быть покрыто тестом с выходом за границы.
- B: «решатель», который не запускает физику, выглядит как решатель
  только на скриншотах; критерий приёмки — `res.solved` реального
  `runSim` и финишное время в пределах горизонта, а не наличие
  прогресс-бара.
- A: самая дисциплинированная декомпозиция, но UI остался тремя
  несобранными файлами. Урок этой сессии: точка входа и сквозной
  прогон (хотя бы jsdom-smoke) должны появляться раньше, чем доводка
  отдельных модулей.
